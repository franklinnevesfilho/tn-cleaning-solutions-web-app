**Change 2 — maintain the marker on the form's cancel path, and guard that write
(currently `:712-729`).**

> **WIDENED 2026-09-22 (AMD-5).** Parts A and B below are what shipped. Part A is as originally
> planned. **Part B — the compare-and-set and the disambiguating re-read — was not in the original
> plan; it was added by the post-implementation code review, and it is now REQ-028.** The original
> text of this change was Part A alone, preserved verbatim there.

**Part A — write the marker (original text, unchanged).**

`updateAppointment` is the **second** way into `cancelled` (`05-CONTEXT.md §2.9`). Add one field to
the `.update({...})` object, after `status`:

```ts
status_before_cancel: parsed.data.status === 'cancelled' ? existingAppointment.status : null,
```

- When the admin picks *Cancelled* in the form, the marker records what the row was a moment ago.
  Change 1 guarantees `existingAppointment.status` is `'scheduled'` or `'in_progress'` here, so the
  domain CHECK cannot fire.
- In **every** other case the marker is written to `null`. That is deliberate and not dead: writing
  it unconditionally is what keeps the coherence invariant self-healing, and it costs nothing.
- Do **not** add a branch for `existingAppointment.status === 'cancelled'`. Change 1 makes it
  unreachable, and constitution §14 forbids handling a state a guard already makes impossible.

**Part B — compare-and-set the whole update, and disambiguate a zero-row result (REQ-028).**

Part A alone is not safe. The status it copies was read at `:633-638`, many statements earlier.
If the row is marked `completed` in another tab in between, this update writes `status = 'cancelled'`
with a stale `status_before_cancel = 'scheduled'` — the completion destroyed and the marker
asserting a falsehood, which is the identical silent loss REQ-024 and REQ-025 close on the button
path. The form always submits a `status`, so the same stomp happens on an edit that only changes the
notes field.

1. Add `.eq('status', existingAppointment.status)` to the appointment `.update(...)`, beside the
   existing `.eq('id', id)` and `.eq('is_archived', false)`. It guards **every** non-`series` edit,
   not only the ones that select *Cancelled*.
2. The update already ends `.select(...).maybeSingle()`, so a guard miss now returns no row —
   indistinguishable, at that point, from an appointment that was archived or deleted. **Re-read the
   row by `id` and `is_archived = false` before returning**, and pick the message from the answer:
   - row still there → `{ success: false, error: 'The appointment changed while you were editing it.
     Refresh and try again.' }`
   - no row → `{ success: false, error: 'Appointment not found.' }`
   - the re-read itself errors → return `error.message`.

   Without the re-read a lost update is reported as a missing appointment, which sends the admin
   looking for a deletion that never happened.
3. Everything downstream — the assignment reconcile (Change 5), the `future`-scope regeneration and
   both `revalidatePath` calls — stays **behind** the successful update, so a lost update changes no
   crew and no occurrence.
4. Unlike the detail page, this error **is** visible: `appointment-form.tsx` is a Client Component
   using `useActionState` and rendering `state.error` (`:85`, `:153-159`). That asymmetry is KL-03
   in `REQUIREMENTS.md`, not an oversight.

The `series` edit scope is untouched: it updates `recurrence_series`, never the appointment row.

**Change 3 — `cancelAppointment` refuses a completed appointment and records the prior status
(currently `:895-920`).**

The action must read before it writes, because PostgREST cannot copy a column into another column
in one statement. Follow the **compare-and-set** shape `voidInvoice` / `issueInvoice` /
`markInvoicePaid` already use in `src/lib/actions/invoices.ts` (constitution §12 — existing
conventions win). Keep the existing `requireAdminRole()` → `createAdminClient()` → `revalidatePath`
skeleton and the existing signature and return type.

1. Read the row: `.select('id, status').eq('id', id).eq('is_archived', false).maybeSingle()`.
   On error return `error.message`; on no row return `'Appointment not found.'`.
2. Refuse, in two separate branches with distinct messages:
   - `status === 'completed'` → `{ success: false, error: 'A completed appointment cannot be
     cancelled. Completed is a final status.' }`
     > **Corrected 2026-09-22 (AMD-5), wording only.** The plan originally specified
     > *"…Change its status first if this was recorded in error."* The code review found that
     > sentence names a remedy the UI forbids: the edit page refuses a `completed` appointment
     > (`edit/page.tsx:178-181`), so there is no way for an admin to change its status. The shipped
     > string is the one above. No behaviour changed and no requirement quoted the old text.
   - `status === 'cancelled'` → `{ success: false, error: 'This appointment is already
     cancelled.' }`
     This second branch is **not** optional and is not a §14 violation: without it the update below
     would try to write `status_before_cancel: 'cancelled'` and raise `23514`, and the state is
     reachable from a stale page or a double submit.
3. Update with the compare-and-set:

```ts
.update({ status: 'cancelled', status_before_cancel: current.status })
.eq('id', id)
.eq('is_archived', false)
.eq('status', current.status)
.select('id')
.maybeSingle()
```

   **The `.eq('status', current.status)` is load-bearing, not ceremony.** Without it, an admin
   cancelling in one tab while another tab marks the appointment complete would overwrite the
   completion and record `status_before_cancel = 'scheduled'` — the exact silent loss this phase
   exists to close, reintroduced through the back door. When the update returns no row, return
   `{ success: false, error: 'The appointment changed while you were cancelling it. Refresh and try
   again.' }`.
4. Keep both existing `revalidatePath` calls and the `{ success: true, data: { id } }` return,
   unchanged, on the success path only.

**Change 4 — `uncancelAppointment` restores the recorded status (currently `:922-948`).**

Same shape.

1. Read `.select('id, status, status_before_cancel').eq('id', id).eq('is_archived', false)
   .maybeSingle()`. Error → message; no row → `'Appointment not found.'`.
2. If `status !== 'cancelled'` → `{ success: false, error: 'This appointment is not cancelled.' }`.
3. `const restoredStatus = current.status_before_cancel ?? 'scheduled'`. **The `?? 'scheduled'`
   fallback is the documented behaviour for a row cancelled before this phase shipped** (the
   Frozen contract's "NULL means not recorded"). It is not a defensive guess and must not be
   removed, logged as an anomaly, or turned into an error.
4. Update `{ status: restoredStatus, status_before_cancel: null }`, filtered
   `.eq('id', id).eq('is_archived', false).eq('status', 'cancelled')` — that last filter is the
   existing compare-and-set and stays. `.select('id').maybeSingle()`; no row → `{ success: false,
   error: 'The appointment changed while you were reopening it. Refresh and try again.' }`.
5. Keep both `revalidatePath` calls and the success return unchanged.

**Change 5 — replace the assignment delete-and-reinsert with a reconcile (currently `:739-764`).**

This is the change that matters most in the phase (`05-CONTEXT.md §4.3`, D-39). It fixes a live
data-loss bug on ordinary `scheduled` appointments and is independent of everything above.

Delete the unconditional `.delete().eq('appointment_id', id)` and the unconditional re-insert.
In their place:

1. Read every assignment row for this appointment:
   `.from('appointment_employees').select('id, employee_id').eq('appointment_id', id)`.
   **No `is_archived` filter** — the delete it replaces had none, and adding one would strand an
   archived row for a removed employee and duplicate an employee who has one. On error, return
   `error.message` exactly as the old delete did.
2. Compute two sets, inline, from `parsed.data.employee_ids` (already de-duplicated by `uniqueIds`
   at `:314` — do not re-implement that):
   - `staleAssignmentIds` — the `id` of every existing row whose `employee_id` is **not** in the
     submitted list.
   - `newEmployeeIds` — every submitted id that has **no** existing row at all.
3. If `staleAssignmentIds.length > 0`, `.delete().in('id', staleAssignmentIds)`; on error return
   `error.message`.
4. If `newEmployeeIds.length > 0`, insert one row per id with `admin_notes: ''`, reusing the
   existing `TablesInsert<'appointment_employees'>[]` typing and the existing error handling
   verbatim.
5. **Every other existing row is left completely alone. Issue no UPDATE against it.** That is what
   preserves `clocked_in_at`, `clocked_out_at`, `admin_notes`, `is_archived` and — just as
   important — the row's `id`, which is the key `employee_clock` and `updateClockTime` address
   (`05-CONTEXT.md §2.5-2.6`).
6. Add **one** short comment (three lines at most) above the reconcile saying why surviving rows are
   never rewritten: clock times and admin notes live on them, and the previous delete-and-reinsert
   destroyed both on every edit. This is the one comment this task adds; the project style is
   otherwise no commentary.

**Duplicate rows are preserved as-is.** `appointment_employees` has no unique constraint on
`(appointment_id, employee_id)` (`05-CONTEXT.md §2.7`), so an employee may legitimately hold more
than one row. If that employee survives the edit, **all** their rows survive; if they are removed,
all their rows are deleted. Do not de-duplicate, do not "clean up", do not add a unique constraint —
collapsing duplicates here would be a silent delete of clock data, which is the bug.

**An empty submitted list still removes every row.** Unchanged from today, and an explicit admin
action.

**The `future` edit scope's own inserts (currently `:849-869`) are untouched** — those rows belong
to freshly created appointments and have no clock data to preserve. Likewise the `series` scope,
which never touches assignments at all.

### Half A — SQL, one serial verifier pass

This runs together with `05-01-PLAN.md`'s E1–E4 on the same reset database, before the user's pass.
Its purpose is narrow: prove that the statements these actions issue are **valid against the
schema**, so that a browser failure can be attributed to the code rather than to the migration.

**S1 — replay `cancelAppointment`'s write.** On a seeded `scheduled` appointment `<A>`:
`UPDATE public.appointments SET status = 'cancelled', status_before_cancel = 'scheduled'
WHERE id = <A> AND is_archived = false AND status = 'scheduled';` → `UPDATE 1`.

**S2 — replay `uncancelAppointment`'s write.**
`UPDATE public.appointments SET status = 'scheduled', status_before_cancel = NULL
WHERE id = <A> AND is_archived = false AND status = 'cancelled';` → `UPDATE 1`, and the row is back
to its seeded state.

**S3 — replay the reconcile against a row that carries clock data.** Pick a seeded assignment,
stamp it (`UPDATE public.appointment_employees SET clocked_in_at = now(), admin_notes = 'keep me'
WHERE id = <X>;`), then run only the two statements the reconcile would issue for an edit that keeps
that employee and adds nobody: **none**. Assert the row is untouched:
`SELECT id, clocked_in_at, admin_notes FROM public.appointment_employees WHERE id = <X>;` returns
the same `id`, a non-null `clocked_in_at` and `'keep me'`. Leave this row in place — the user's
script reads it.

Half A **cannot** prove REQ-024, REQ-026 or REQ-027: every one of them lives in a server action,
which is not reachable from SQL and not reachable by URL.

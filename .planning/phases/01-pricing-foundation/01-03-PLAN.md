hide it.** Do not add a placeholder, a "pay TBD" row, an estimated earnings figure, or any other

### Objective

### What to do

Write the migration exactly as the four parts in `01-CONTEXT.md` "Migration B" specify. Before
writing a line of it, read `supabase/migrations/20260917120000_secure_appointment_employees_view.sql`
end to end and follow it statement for statement — style, quoting, and a comment block above each
non-obvious statement explaining *why*.

Five things in it are load-bearing and easy to get wrong:

1. **The row filter lives inside each view body.** The caller has no SELECT policy on either base
   table any more, so definer rights would otherwise turn a column restriction into a full-table
   read. `jobs_employee_view` carries `WHERE NOT is_archived`; `appointments_employee_view` carries
   the dropped policy's filter from `:574` verbatim, admin branch included.
2. **`security_invoker='false'` is deliberate.** An invoker-rights view returns nothing, because the
   caller has no policy on the base table.
3. **`REVOKE ALL` then `GRANT SELECT` is not cosmetic.** Postgres default privileges hand out
   `GRANT ALL`, and a definer view with write privileges is auto-updatable — any authenticated user
   could write to `jobs` or `appointments` through it. That exact bug is what `20260917120000_*`
   fixed for `employees_employee_view`.
4. **Column lists are explicit; never `SELECT *`.** `appointments_employee_view` names its thirteen
   columns. A `*` view would inherit `billed_price_cents` the instant migration A adds it, silently
   reopening the leak this migration exists to close. `price_override_cents` and
   `billed_price_cents` are the two columns that must not appear.
5. **Part 3, the `client_locations` repair, is mandatory and is the thing most likely to be
   skipped.** `"Employee select locations for assigned appointments"` (`:586-588`) subqueries
   `public.appointments` inside its `USING` clause, and Postgres applies that table's RLS there.
   Drop the appointments policy without this repair and every employee silently loses the location
   address on their schedule — a visible regression with no compile error and no failing query, just
   a missing line of text. `01-RESEARCH.md §12b` has the full reasoning. Verify it empirically: as a
   seeded employee, `GET /rest/v1/client_locations?select=*` must return the same rows before and
   after your migration.

Carry the **verified** DOWN SQL in the header comment (the four-step order is in `01-CONTEXT.md`
part 4 — the policy must be dropped before its function) and actually run it once against a reset
DB, then `supabase db reset` again.

### What to do

**Primary approach — aliased view embeds.** In each query make two substitutions:
- `appointments!inner (` → `appointments:appointments_employee_view!inner (`
- `jobs!inner (` → `jobs:jobs_employee_view!inner (`

The aliases keep the returned JSON keys as `appointments` and `jobs`, so the local
`AppointmentRecord` / `TimeSheetRecord` types (`schedule/page.tsx:22`, `schedule/[id]/page.tsx:21`,
`time-sheets/page.tsx:8`) and every consumer of them (`schedule/page.tsx:189,235,266-267`,
`schedule/[id]/page.tsx:233,271-273`, `time-sheets/page.tsx:123`) need **no change at all**. That is
the whole reason to alias rather than rename.

`clients!inner` and `client_locations` are untouched — employees keep base-table policies on both.
`client_locations` only keeps working because 01-03-T1 repaired its policy; if addresses vanish,
that repair is missing, and that is T1's bug, not yours. Report it rather than working around it.

**This may not work (B-05 / AS-10).** Both substitutions ask PostgREST to infer a relationship
between two views, which carry no foreign keys. The view→table direction is proven in this stack
today; view→view is not. Test each one independently — it is entirely possible that one resolves
and the other does not.

**Fallback, per embed, if you get `PGRST200` / "Could not find a relationship":**

*If `appointments:appointments_employee_view` fails* — reverting to a plain `appointments!inner` is
not an option, because the employee has no policy on that table any more. Split the query instead:
1. Select `appointment_id` from `appointment_employees_employee_view` as today, dropping the
   `appointments` embed entirely.
2. `supabase.from('appointments_employee_view').select('id, job_id, location_id, scheduled_date,
   scheduled_start_time, scheduled_end_time, status, notes, clients!inner(name, phone),
   client_locations(label, address)').in('id', appointmentIds)` — the view exposes `job_id` and
   `location_id` precisely so this works without a schema change.
3. Stitch in JS into the same `appointments: { ... }` shape the local types already declare.

*If `jobs:jobs_employee_view` fails* — split the job lookup out:
1. Add `job_id` to whichever appointments select you ended up with and drop the `jobs` embed.
2. `supabase.from('jobs_employee_view').select('id, name, description').in('id', jobIds)`.
   For `time-sheets/page.tsx`, only `name` is needed.
3. Stitch into the same `jobs: { name, description }` shape.

Skip a follow-up round-trip entirely when its id list is empty. Preserve each file's existing
error-handling shape exactly — the "error path" column in the table above.

## Verification (for `verifier`)

### Changed-risk surface

Two live RLS policies are **removed** from two tables that three production employee screens read
through, and a third policy that transitively depends on one of them is rewritten. Four ways this
goes wrong, in descending order of cost:

1. **A view does not resolve and employees see an error card instead of their schedule** — a total
   outage of the employee product, in a milestone nominally about admin pricing. The risk doubled
   with option (b): two view→view embeds now, neither proven in this stack.
2. **The `client_locations` policy repair is missing or wrong** and employees silently lose the job
   site address. No error, no failing query, no compile error — just a missing line of text on a
   screen nobody on the build side looks at. **This one will not surface unless you look for it.**
3. **A definer view left writable** — an RLS bypass strictly worse than the column leak it was
   created to close.
4. **A price column still reachable.** `SELECT *` on a view, or an over-generous column list, leaves
   REQ-020 unmet while every screen looks perfect.

### What to do

**`src/lib/pricing/money.ts`** — no imports, erasable syntax only.
```ts
export function parseDollarsToCents(raw: string): number | null
export function formatCents(cents: number): string
export function formatRate(cents: number): string
export function durationMinutes(startTime: string, endTime: string): number
export function hourlyAmountCents(rateCents: number, minutes: number): number
```
- `parseDollarsToCents`: trim; empty → `null`; `Number(raw)` NaN / non-finite / `< 0` → `null`;
  otherwise `Math.round(value * 100)`. This replaces all three existing parsers
  (`appointments.ts:82-93`, `invoices.ts:66-77`, the inline block in `jobs.ts:62-93`) — Phase 2
  deletes them. Document the deliberate contract change in a comment: the appointments variant
  currently distinguishes `null` (absent) from `'invalid'`; this single function returns `null` for
  both, and callers decide by checking whether the raw string was empty first.
- `formatCents`: one module-level
  `Intl.NumberFormat('en-US', { style: 'currency', currency: 'USD' })`, matching
  `jobs-list.tsx:20-23`. `formatCents(4500) === '$45.00'`.
- `formatRate(cents)`: `formatCents(cents) + '/h'` → `'$45.00/h'`. **No mode parameter** — there are
  no modes (constitution §8).
- `durationMinutes`: accepts `'HH:MM'` and `'HH:MM:SS'` (PostgREST returns `time` as `HH:MM:SS`;
  the forms submit `HH:MM`). Returns whole minutes, `end - start`, seconds ignored. Same parsing
  shape as `compareTimes` at `appointments.ts:76-80`.
- `hourlyAmountCents`: `Math.round((rateCents * minutes) / 60)`. Multiply **before** dividing — that
  keeps the intermediate an exact integer in float64 for any realistic input. Never
  `rateCents * (minutes / 60)`.

There is no `PricingMode` type. Do not create one.

**`src/lib/pricing/resolve.ts`** — no imports beyond `./money.ts`, erasable syntax only.
```ts
export type JobPricing = {
  hourly_rate_cents: number
}

export type ClientJobRule = {
  hourly_rate_cents: number
  effective_from: string       // 'YYYY-MM-DD'
  is_archived: boolean
}

export type PriceSource = 'appointment_override' | 'client_job_pricing' | 'job'

export type ResolvedPrice = {
  amount_cents: number
  rate_cents: number | null    // null only for a manual override
  minutes: number | null       // null only for a manual override
  source: PriceSource
}

export function pickEffectiveRule<T extends ClientJobRule>(rules: T[], onDate: string): T | null

export function resolveAppointmentPrice(input: {
  job: JobPricing
  rule: ClientJobRule | null
  minutes: number
  appointmentOverrideCents: number | null
}): ResolvedPrice
```
- `pickEffectiveRule`: filter out `is_archived`, keep `effective_from <= onDate` (plain string
  comparison is correct for zero-padded ISO dates — the codebase already relies on this at
  `appointments.ts:153,284`), return the greatest `effective_from`, else `null`.
- `resolveAppointmentPrice` precedence: **override → rule → job**, exactly as written in
  `01-CONTEXT.md` "The two prices".
  - override non-null → `{ amount_cents: override, rate_cents: null, minutes: null,
    source: 'appointment_override' }`
  - rule non-null → `{ amount_cents: hourlyAmountCents(rule.hourly_rate_cents, minutes),
    rate_cents: rule.hourly_rate_cents, minutes, source: 'client_job_pricing' }`
  - otherwise the same from `job.hourly_rate_cents` with `source: 'job'`
- The input type deliberately has **no** `billed_price_cents` field. The billed amount is a display
  concern decided by the caller (`01-CONTEXT.md`), and letting the resolver see it would recreate
  the self-referential pricing this milestone exists to remove.
- `job.hourly_rate_cents` is NOT NULL in the schema. Do not add a null guard (constitution §14).

**`src/lib/pricing/lookup.ts`** — the only file here that touches Supabase.
```ts
export async function fetchClientJobRules(
  client: SupabaseClient<Database>,
  pairs: Array<{ clientId: string; jobId: string }>
): Promise<Map<string, ClientJobRule[]>>
```
One query over the distinct `client_id`s and `job_id`s in `pairs`
(`.select('client_id, job_id, hourly_rate_cents, effective_from, is_archived')
.in('client_id', [...]).in('job_id', [...]).eq('is_archived', false)`), keyed in the returned map as
`` `${clientId}:${jobId}` ``, each array left for `pickEffectiveRule` to narrow. Returns an empty
map for empty `pairs` **without issuing a query**. This batched shape exists because three callers
need it — the invoice builder resolves N lines, the appointment detail page resolves 1, and the
appointment *list* resolves a page of rows — all in one round trip each (constitution §13 is
satisfied: the second and third real callers exist in this milestone).

Note the over-fetch: `.in(client) × .in(job)` returns the cross product of the distinct values, not
just the requested pairs. That is correct and intended — it is one query instead of N, and the map
key discards the extras. Say so in a comment so nobody "fixes" it into N queries.

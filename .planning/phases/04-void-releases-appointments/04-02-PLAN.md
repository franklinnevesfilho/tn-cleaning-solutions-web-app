## Task 04-02-T1 — `voidInvoice` releases its appointments and clears their cache

### What to do

`voidInvoice` is at `src/lib/actions/invoices.ts:597-634`. Today it loads the invoice, guards on
`status IN ('draft','issued')`, writes `status = 'void'`, revalidates and returns. It gains two
writes after the status write, in this order and no other:

1. **Release.** Mark this invoice's own live junction rows as released and collect the appointment
   ids in the same round trip:

   ```
   adminClient
     .from('invoice_appointments')
     .update({ is_archived: true })
     .eq('invoice_id', id)
     .eq('is_archived', false)
     .select('appointment_id')
   ```

   The rows are **retained in full** — do not delete them, do not null out
   `billed_amount_cents`, `billed_rate_cents` or `billed_minutes`. The voided invoice must still
   render its original lines and its original `total_cents` (constitution §7, REQ-022(a)).

2. **Clear the cache** for exactly the appointments that write released, by calling the existing
   `clearBilledPriceCache(ids)` (`:262-273`). Do not write your own update; do not widen its
   signature. Per DET-V4 no further guard is needed: after step 1 the partial unique index
   guarantees no other live claim on those appointments exists.

**Ordering, and why it is not negotiable** (`04-CONTEXT.md §6`, OQ-V2). Status first, then release,
then clear. If the release write fails after the status write landed, the invoice is void and its
appointments are still consumed — which is exactly today's behaviour, a state the product has
always had. Releasing *first* would mean that a failed status write leaves a draft or issued
invoice still displaying and totalling lines whose appointments have already been returned to the
billable pool: a double-billing window this phase would have invented. Put that reasoning in a
short comment at the ordering, because it reads backwards otherwise and a future reviewer will
try to "fix" it.

**Error handling** (DET-V5):
- Release write errors → call `revalidateInvoicePaths(id)` (the status really did change; the
  screens must not lie about it), then return
  `{ success: false, error: 'The invoice was voided, but its appointments were not released.' }`.
  Do not claim a retry path — the `status IN ('draft','issued')` guard means a second Void call on
  the same invoice is refused, and that guard is **not** being loosened in this task.
- `clearBilledPriceCache` already logs and swallows its own errors, exactly as
  `writeBilledPriceCache` does. Leave that convention alone (constitution §12). A swallowed failure
  there leaves a stale "Invoiced" chip and nothing worse.
- Do not add handling for states the schema makes impossible (constitution §14). In particular, do
  not handle "no rows released" as an error — voiding a draft invoice that has no lines is legal
  and must succeed.

**`archiveInvoice` and `restoreInvoice` are not touched.** D-24: archival is a visibility flag, not
a statement about whether money was billed, and an archived *paid* invoice is money the client
really was charged. They keep writing `billed_price_cents` never, and they must not learn about
`is_archived` on the junction table. This is the single most likely wrong "improvement" in this
task.

**Note for the implementer, from `04-CONTEXT.md §4`:** this is the **first `UPDATE` this
application has ever run against `invoice_appointments`.** Every other write path deletes and
re-inserts. That table carries a `set_updated_at` BEFORE UPDATE trigger that raised
`record "new" has no field "updated_at"` on every UPDATE until `20260918120000` added the column.
The column exists now, so the update works (AS-12) — but it is **assumed, not proven**, and you are
not the one who proves it: per `04-CONTEXT.md §7.0` you start no database. Say so in your report,
and name browser step 6 (Void) as where it would surface if the assumption is wrong.

Per `04-CONTEXT.md §9`, read `node_modules/next/dist/docs/01-app/01-getting-started/07-mutating-data.md`
and `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/revalidatePath.md` before
editing this file, and heed any deprecation notice.

## Verification (for `verifier`)

### Changed-risk surface

The rule that stops an appointment being billed twice is being relaxed, in an action and in two
queries, at the same time as the index behind it is replaced. The failure worth hunting is not
"released visits do not come back" — that is loud and obvious — it is the opposite: **a live claim
that stops being enforced.** Check the negative cases as hard as the positive ones. The second
risk is D-24: a well-meaning agent extending the release to `archiveInvoice`, which would show a
live derived price in place of an amount a client really paid.

```bash
npm run lint
npx tsc --noEmit
```

section — E1 through E6 — which proves the schema half, **run in the same single serial pass**
(`04-CONTEXT.md §7.0`; the verifier is the only actor that touches the local database). What
follows proves the action half, and needs the app.

The user's browser script below starts from that clean database and builds its own state. Do not
